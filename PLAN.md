# План проекта «108М» — расписание, оценки, ДЗ, дежурства и замены

Статус: **планирование**. На этом этапе код не переписывается. Реализация выполняется отдельными пунктами, чтобы после каждого шага можно было проверить результат.

## 0. Зафиксированные ограничения и решения

1. Группа — **108М**, состоящая из двух списков английского языка: **2к207** и **2к202**. На остальных занятиях группа занимается вместе.
2. Фронтенд — статический сайт на GitHub Pages. Он не обращается к backend по URL и не содержит секретов.
3. Backend — один запускаемый файл `bot.py` на Aurorix. Внутри файла допускаются отдельные логические модули/классы, но запуск должен оставаться `python bot.py`.
4. Все записи выполняет Telegram-бот. Фронтенд только читает JSON-файлы из репозитория.
5. Gemini вызывается только ботом, никогда браузером.
6. Фото журнала принимаются через Telegram как изображения или документы-изображения. PDF и прочие файлы для распознавания журнала не принимаются.
7. PDF замен может скачиваться ботом из VK и обрабатываться отдельно от фотографий журнала.
8. Часовой пояс — `Europe/Moscow`. Расписание задач бота: примерно в **20:00** и **24:00** по Москве.
9. Данные разделяются на несколько небольших JSON-файлов. Для согласованности используется общий `manifest.json` с версией публикации.
10. Источник истины — сохранённые данные в GitHub, а не повторный вызов Gemini при каждом открытии сайта.
11. В репозиторий, этот план, логи и frontend нельзя записывать Telegram-, GitHub- или Gemini-секреты. Они должны передаваться только через переменные окружения Aurorix. Секреты, которые уже отправлялись в переписке, не использовать; перед запуском их нужно заменить.

### Ограничение приватности

Статический GitHub Pages без авторизации не может технически отличить участника 108М от любого другого посетителя. Если JSON опубликован вместе с сайтом, оценки и ФИО сможет прочитать любой, кто найдёт URL или репозиторий. Текущий план предусматривает открытый просмотр по URL, потому что авторизация не требуется, но это ограничение необходимо осознанно принять. Настоящее ограничение «только группе 108М» возможно только после добавления авторизации или закрытого backend.

## 1. Фронтенд GitHub Pages

### 1.1. Общая оболочка сайта

Сделать интуитивную мобильную страницу с нижней или верхней навигацией:

- **Расписание**;
- **Оценки**;
- **Домашние задания**;
- **Дежурства**;
- **Замены**.

На каждой странице должны быть состояния `загрузка`, `нет данных`, `ошибка загрузки` и нормальное состояние. Приложение не должно молча показывать старые локальные данные как официальные.

Создать единый загрузчик JSON:

1. загрузить `manifest.json`;
2. получить номера версий файлов;
3. загрузить только необходимые файлы;
4. добавить версию к URL (`?v=...`), чтобы GitHub Pages/CDN не показывал старую публикацию;
5. проверить совпадение `revision` у файлов;
6. при несовпадении повторить загрузку и показать понятное сообщение.

На первом этапе можно использовать текущие `index.html`, `styles.css`, `app.js`, но расписание и задания нужно убрать из жёстко прописанных дубликатов и читать из JSON.

### 1.2. Расписание

Показать недели с кнопками назад/вперёд и кнопкой возврата к текущей неделе.

Для каждой пары показывать:

- номер пары;
- время начала и конца;
- предмет;
- преподавателя;
- кабинет;
- отметку подгруппы, если занятие относится к английскому;
- отметку `числитель`/`знаменатель`;
- замену, если она действует на конкретную дату.

«Россия — мои горизонты» и классный час отображаются как отдельные события, но не должны ошибочно попадать в оценки как обычный предмет.

### 1.3. Выбор ученика и оценки

Сделать выбор:

1. группа/подгруппа — 2к207 или 2к202;
2. ученик;
3. период — текущая аттестация, предыдущая аттестация, все периоды;
4. предмет.

На экране ученика показать:

- оценки по датам;
- `5`, `4`, `3`, `2`;
- `н/б` как посещаемость/отсутствие;
- незначимые точки не показывать;
- итоговую отметку аттестации, если в журнале есть маркер `А`;
- отдельно обычные оценки и итог аттестации;
- предупреждение о низкой уверенности или конфликте, если такая запись ещё не подтверждена;
- дату последнего обновления.

Не путать рукописные `Н` и `4`. В канонические оценки попадают только разрешённые значения. Неразборчивое значение сохраняется как требующее проверки, но не превращается автоматически в оценку.

### 1.4. Домашние задания

Показывать ДЗ под конкретным уроком и датой, а не только отдельным общим списком.

Для каждого задания отображать:

- предмет;
- текст;
- дату выдачи;
- дату следующего урока;
- статус: актуальное, выполненное, просроченное или перенесённое из-за замены.

### 1.5. Дежурства

Показать:

- кто выбран дежурным сегодня;
- кто фактически засчитан дежурным;
- количество дежурств каждого ученика;
- историю по датам;
- причину статуса: `выбран`, `подтверждён сообщением`, `не подтверждён`, `ожидает проверки`.

Обновление должно быть детерминированным: обновление страницы не меняет выбранных людей.

### 1.6. Замены

Показать на выбранную дату:

- обычное занятие;
- новое занятие;
- кабинет;
- источник и время обновления;
- числитель/знаменатель.

Если для 108М замены нет, отображается обычное расписание, а не пустая таблица.

### 1.7. Адаптивность и доступность

- корректная работа на телефоне;
- крупные зоны нажатия;
- горизонтальная прокрутка только у широких таблиц оценок;
- контрастные цвета для оценок и замен;
- подписи для screen reader;
- не вставлять неэкранированный текст из Telegram или VK через `innerHTML`.

## 3. JSON-файлы и формат данных

Рекомендуемая структура репозитория:

```text
data/
  manifest.json
  students.json
  schedule.json
  grades.json
  tasks.json
  duties.json
  replacements.json
  reviews.json
```

`tasks.json` можно оставить совместимым с текущим сайтом или перенести в `data/tasks.json`; после переноса frontend должен использовать только один источник.

### 3.1. Общие правила

- даты только `YYYY-MM-DD`;
- время — ISO с часовым поясом либо отдельное московское время;
- у каждого файла `schemaVersion`, `revision`, `generatedAt`;
- UTF-8, `ensure_ascii=false`, стабильная сортировка ключей;
- идентификаторы не зависят от ФИО, написанных с ошибкой;
- персональные данные и оценки не отправляются в логи;
- исходные фотографии не публикуются в GitHub.

### 3.2. `students.json`

Хранит `studentId`, отображаемое ФИО, группу и подгруппу английского. Историю переименований можно хранить в `aliases`, чтобы старые записи не потеряли ученика.

Для распознавания допускаются алиасы, опечатки и падежные варианты, но при неоднозначности запись уходит на проверку.

### 3.3. `schedule.json`

Каждая пара получает стабильный `lessonId` и содержит:

- weekday;
- pairNumber;
- start/end;
- subjectId и название;
- teacher;
- room;
- subgroup;
- `weekType`: `all`, `numerator`, `denominator`;
- период действия;
- признак служебного события.

### 3.4. `grades.json`

Ключ оценки:

```text
studentId + subjectId + lessonDate + entryType
```

`entryType` — `daily`, `attendance` или `attestation`.

Каждая запись хранит:

- каноническое значение;
- исходный символ;
- confidence;
- источник и hash изображения;
- модель и версию prompt/schema;
- время распознавания;
- состояние `confirmed`, `automatic`, `pending`, `conflict`;
- список доказательств, если одно и то же значение встретилось на нескольких фото.

Разрешённые канонические значения: `2`, `3`, `4`, `5`, `н/б`. Точка и прочие незначимые символы не становятся оценкой. Маркер `А` означает границу/итог аттестации и сам по себе не является оценкой.

### 3.5. `reviews.json`

Хранит нерешённые варианты:

- старое значение;
- новое значение;
- confidence каждого варианта;
- ученик, предмет и дата;
- причина сомнения;
- кнопки/решение пользователя;
- время решения.

Это позволяет при следующем заполнении журнала предложить изменение низкоуверенной оценки, не перезаписывая старое значение автоматически.

### 3.6. `duties.json`

Хранит:

- счётчик каждого ученика;
- выбранных на дату;
- фактически подтверждённых;
- seed и версию алгоритма;
- сообщения-источники в безопасном сокращённом виде;
- статус дня.

### 3.7. `replacements.json`

Хранит дату, тип недели, исходный `lessonId`, новое занятие, кабинет, группу, источник, hash/URL вложения и время получения. Замена имеет срок действия и не изменяет базовое расписание навсегда.

### 3.8. `manifest.json`

Содержит список файлов и одну общую `revision`. Бот публикует новые данные сначала во временную/новую ревизию, затем обновляет manifest последним. Frontend использует только согласованный набор файлов.

## 4. Архитектура Telegram-бота

Поток данных:

```text
Telegram
  -> bot.py на Aurorix
     -> Telegram-авторизация и очередь
     -> нормализация изображений
     -> Gemini / парсеры заданий / парсер дежурств
     -> валидация и разрешение конфликтов
     -> GitHub Contents API
        -> JSON в репозитории
           -> GitHub Pages
```

### 4.1. Доступ

- разрешённые Telegram user ID задаются переменной окружения через список из трёх ID;
- usernames не использовать как идентификатор: они могут измениться;
- привязка Telegram-аккаунта к конкретному ученику не нужна;
- все разрешённые пользователи могут отправлять фото, ДЗ, отчёты о дежурствах и команды;
- отсутствие пользователя в allowlist проверяется до скачивания фото и до вызова внешнего API;
- сообщения об ошибках не должны раскрывать токены, полные ответы API или внутренние пути.

### 4.2. Команды

Минимальный набор:

- `/start` — краткое описание;
- `/help` — полная инструкция и примеры синтаксиса;
- `/grades` — справка по просмотру оценок;
- `/duties` — выбранные и фактические дежурства;
- `/today` — расписание, замены и ДЗ на сегодня;
- `/review` — список конфликтов и низкоуверенных записей;
- `/cancel` — отменить незавершённую загрузку фото;
- `/status` — очередь, последнее обновление, квота Gemini.

Для подтверждений использовать inline-кнопки, но не делать подтверждение обязательным для каждой однозначной оценки.

### 4.3. Сбор альбома фотографий

Принимать фото как отдельные сообщения и как Telegram-альбомы. Поскольку отдельной кнопки завершения не требуется:

1. бот создаёт batch для пользователя;
2. добавляет новые изображения в течение небольшого окна тишины;
3. после отсутствия новых изображений запускает обработку;
4. максимум — 20 файлов на один batch;
5. повторное изображение определяется по hash и не отправляется в Gemini второй раз;
6. новую загрузку можно начать следующим сообщением или командой `/cancel`.

Нужно предусмотреть защиту от слишком больших файлов и понятное сообщение, если изображение не удалось скачать.

## 5. Распознавание журнала через Gemini

### 5.1. Нормализация изображения

До Gemini:

1. проверить MIME и размер;
2. скачать только разрешённый тип изображения;
3. применить EXIF orientation;
4. определить, не является ли изображение повёрнутым на 90/180/270 градусов;
5. повернуть, выровнять и сжать копию;
6. убрать лишние метаданные;
7. не хранить исходник дольше необходимого.

Если первый результат невалиден или имеет низкую уверенность, разрешается ограниченный fallback с альтернативными поворотами. Все четыре варианта постоянно отправлять нельзя: это расходует квоту.

### 5.2. Контекст для Gemini

В запрос передаются:

- изображение или небольшая группа изображений;
- группа 108М;
- эталонный список учеников и стабильные IDs;
- предмет/страница, если они уже определены;
- правила допустимых значений;
- уже сохранённые оценки только для соответствующего участка журнала;
- требование не изменять существующее значение без отдельного кандидата;
- строгая JSON Schema;
- инструкция не додумывать отсутствующие клетки.

Если на фото нет части журнала, отсутствующие клетки не удаляются и не заменяются пустыми значениями.

### 5.3. Формат ответа

Gemini возвращает JSON примерно такого вида:

```json
{
  "document": {
    "group": "108M",
    "subject": "Химия",
    "orientation": 0
  },
  "cells": [
    {
      "studentHint": "Аглиуллина Самира",
      "studentId": "...",
      "date": "2026-11-13",
      "raw": "5",
      "value": "5",
      "entryType": "daily",
      "confidence": 0.96,
      "alternatives": [],
      "reason": ""
    }
  ],
  "warnings": []
}
```

Фактическая схема должна быть строже: неизвестные поля допустимы только в `metadata`, а значение проверяется enum-валидатором. Markdown вокруг JSON запрещается; если Gemini его всё же прислал, бот извлекает JSON и валидирует его повторно.

### 5.4. Квоты и стабильность

Параметры квоты пользователя учитывать как локальные ограничения: примерно 5 RPM, 20 RPD и 250k TPM. Нельзя полагаться на то, что эти значения постоянны у Google.

Нужны:

- последовательная очередь с ограниченной параллельностью;
- счётчики минутной и суточной квоты;
- дедупликация по hash изображения;
- ограничение размера запроса;
- повтор только для 429/503 с задержкой;
- ограниченное количество retries;
- остановка автоматических fallback-запросов при приближении к лимиту;
- сохранение результата, чтобы не распознавать фото при каждом открытии сайта;
- модель, prompt и schema с версиями.

Список моделей задаётся настройкой и использует названия, подтверждённые в Google AI Studio пользователя: `gemini-3.5-flash-lite`, `gemini-3.8-flash`, `gemini-3.6-flash`, `gemini-3-flash`. При ошибке недоступности модели бот пробует следующую только если это разрешено лимитом.

### 5.5. Слияние с уже существующими оценками

Для ключа `studentId + subjectId + date + entryType`:

1. одинаковая новая оценка не создаёт дубликат;
2. при повторном подтверждении того же значения увеличивается количество доказательств и итоговая уверенность;
3. старое подтверждённое значение не изменяется автоматически;
4. новое отличающееся значение становится кандидатом в `reviews.json`;
5. если старое значение было низкоуверенным, новое более уверенное предлагается для замены, но до подтверждения остаётся старое;
6. ручное подтверждение имеет максимальный приоритет;
7. если Gemini не увидел клетку, существующая оценка не удаляется;
8. конфликт с почти равными вариантами требует подтверждения, а не угадывания.

### 5.6. Итог ответа пользователю

После обработки бот сообщает:

- сколько страниц обработано;
- сколько новых оценок добавлено;
- сколько совпало с существующими;
- сколько низкоуверенных;
- сколько конфликтов;
- какие страницы не распознаны.

В публичный JSON попадают только валидные записи. Сырые фото и полные промпты не коммитятся.

## 6. Дежурства

### 6.1. Начальное состояние

На старте все счётчики равны 0. Позже их можно изменить отдельной командой или подготовленным JSON, но исторические даты не должны пересчитываться без явного действия.

Рабочие дни — понедельник–пятница. Суббота включается только явным ручным исключением, так как обычное расписание её не отображает.

### 6.2. Выбор в 00:00

В полночь по Москве backend создаёт выбор на текущую дату:

1. найти минимальное количество дежурств;
2. выбрать двух человек;
3. если минимальных больше двух — выбрать двоих детерминированно-случайно;
4. если минимальный только один — выбрать его обязательно, второго выбрать случайно из ближайшего минимального слоя;
5. если минимальных ровно два — выбрать обоих;
6. сохранить итог в `duties.json`.

Seed рассчитывается из даты, группы, версии списка учеников и версии алгоритма через SHA-256. Использовать встроенный Python `hash()` нельзя, потому что он меняется между запусками процесса.

В результате сохраняются seed и выбранные ученики, поэтому перезагрузка страницы не меняет выбор. Изменение списка учеников не должно менять уже закрытые исторические даты.

### 6.3. Сообщение о фактически дежуривших

Любой разрешённый пользователь может отправить сообщение вида:

```text
Дежурили Аббакаев, Бадреев, Осадчий
```

Распознавать:

- фамилию;
- имя;
- ФИО;
- небольшие опечатки;
- разные окончания и регистр;
- несколько человек в одном сообщении.

Правила:

- совпадение по одному имени разрешено только если оно уникально;
- одна буква вроде `А` не считается учеником;
- при почти равных кандидатах отправляется запрос подтверждения;
- принимать 3–5 названных человек и другие явно перечисленные количества;
- засчитывать только названных людей, а не выбранных автоматически;
- если сообщение не содержит уверенно распознанных имён, ничего не засчитывать;
- если есть несколько противоречивых отчётов, использовать последний однозначный либо запросить подтверждение.

### 6.4. Закрытие дня в 24:00

В конце дня:

- если есть подтверждённый отчёт — увеличить счётчики только названным людям;
- выбранные, но не названные люди не получают автоматическое дежурство;
- если отчёта нет — день закрывается без начисления;
- неоднозначные имена остаются в `pending`;
- повторная обработка полуночи идемпотентна и не увеличивает счётчики дважды.

При перезапуске bot.py должен восстановить незакрытые даты из `duties.json` и догнать пропущенную обработку.

## 7. Домашние задания

### 7.1. Допустимый синтаксис

Основной формат:

```text
Математика Выучить логарифмы
```

Дата может быть в конце:

```text
Математика Выучить логарифмы 10.09
```

Допустимый вариант без даты означает дату фактической отправки.

### 7.2. Правило даты

- дата отправки/указанная дата — дата выдачи;
- ДЗ появляется на **следующем уроке** предмета строго после даты выдачи;
- для `Математика ... 10.09` ближайший урок математики после 10.09 получает ДЗ;
- если урок отменён заменой, он не считается ближайшим, ДЗ переносится на следующий действующий урок;
- в расчёте учитываются числитель/знаменатель, кабинет не меняет предметный `subjectId`.

### 7.3. Обработка текста

- нормализовать регистр, `ё/е`, пробелы и пунктуацию;
- поддержать небольшие опечатки;
- поддержать очевидные сокращения, например `Введ` → «Введение в специальность»;
- если найдено несколько предметов, попросить разделить их на разные сообщения;
- `/help` всегда показывает правильный синтаксис;
- дубликат не создавать, а сообщить, что такое ДЗ уже есть;
- изменение существующего ДЗ должно обновлять запись и сообщать об этом;
- обработка Telegram update должна быть идемпотентной.

## 8. VK и PDF замен

### 8.1. Поиск поста

Каждый вечер примерно в 20:00 бот ищет в открытой группе VK публикацию с формой:

```text
КГАМТ им. Л.Б. Васильева
Замены на DD.MM.YYYY
.pdf
```

Искать нужно по дате, заголовку и PDF-вложению. Обрабатывать самый подходящий пост, а не произвольный свежий пост. Если открытый способ VK недоступен, бот сообщает об этом и предлагает переслать ссылку/файл разрешённому пользователю; браузерный Selenium не является обязательной частью проекта.

### 8.2. Обработка PDF

- скачать PDF во временный каталог;
- не запускать его как программу и не выполнять вложенный код;
- сначала извлечь текст и таблицу локально;
- при плохом текстовом слое использовать безопасный рендер страниц в изображение и OCR;
- сохранить только распарсенные замены и технический hash;
- PDF не публиковать на GitHub без отдельной необходимости.

Структура документа стабильна, меняется в основном дата. Заголовок содержит `числитель` или `знаменатель`.

### 8.3. Фильтрация 108М

В PDF могут быть десятки строк других групп. Бот обязан фильтровать только `108М` и не применять строки, относящиеся к другим группам. Пример с заменами для `109М` не должен изменять расписание 108М.

Если в документе нет строки 108М, для 108М не создаётся замена. Особые правила недели применяются только явно настроенными правилами, а не на основании похожего номера группы.

### 8.4. Правила знаменателя для 108М

При знаменателе:

- в четверг последняя соответствующая пара: вместо истории 227 — информатика 406;
- в пятницу физкультура заменяется математикой в кабинете 2к302 согласно слоту на исходной фотографии расписания;
- обычный режим при числителе сохраняется.

Эти правила оформить как записи `replacementRules` с датой, `weekType`, `lessonId`, новым предметом и кабинетом. Не зашивать их в рендеринг frontend.

### 8.5. Время обновлений

- около 20:00 — получить свежий пост/PDF, определить тип недели, распарсить и опубликовать замены;
- в 24:00 — закрыть дежурства, пересчитать относящиеся ДЗ и опубликовать итоговое состояние;
- при запуске после простоя выполнить пропущенные даты в идемпотентном режиме.

## 9. GitHub-хранилище и публикация

Создать отдельный слой `GitHubStorage` внутри `bot.py`:

1. прочитать JSON и SHA;
2. провалидировать схему;
3. выполнить merge;
4. сериализовать стабильно;
5. записать через Contents API с текущим SHA;
6. при конфликте SHA перечитать, объединить и повторить ограниченное число раз;
7. обновить manifest последним;
8. не включать секреты и полные пользовательские сообщения в commit message.

Все операции записи должны иметь `eventId`/`updateId`, чтобы сетевой повтор не создал второй объект.

Если несколько JSON обновляются одной операцией, каждой публикации присваивается единый `revision`. Frontend принимает только одинаковую ревизию. GitHub Pages может обновляться с задержкой, поэтому интерфейс показывает время последней опубликованной версии.

Текущую синхронную запись из async-обработчиков `bot.py` заменить на очередь или выполнять в отдельном worker, чтобы один сетевой запрос GitHub не блокировал Telegram-бота.

## 13. Критерий готовности

Проект считается готовым, когда:

- сайт показывает расписание 108М и корректные замены;
- каждый из 33 учеников выбирается отдельно;
- оценки можно загрузить фотографиями через Telegram;
- боковые фотографии нормализуются;
- Gemini возвращает валидируемый JSON;
- неполный журнал не удаляет имеющиеся данные;
- старые оценки не перезаписываются автоматически;
- низкоуверенные и конфликтные значения можно подтвердить позже;
- ДЗ попадает под следующий фактический урок;
- дежурные выбираются одинаково при повторном открытии сайта;
- в 24:00 начисляются только люди из сообщения «Дежурили ...»;
- VK/PDF замен распознаются только для 108М;
- frontend не содержит секретов и не вызывает закрытый backend;
- повторные сообщения и повторные запуски не создают дубликатов;
- ошибка внешнего сервиса не повреждает уже опубликованные JSON.
